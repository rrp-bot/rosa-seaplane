01 · The proposition

Keep the slow part warm.
Make the useful part self-service.

Provision a configurable number of complete baseline environments ahead of demand. An authenticated API reserves one, applies the requested repository and branch, and gives the caller a checkout. Releasing the checkout destroys that environment; a reconciler builds a clean replacement.

Recommended shape: a small control plane in a new repository, deployed to the environment’s central account. It owns the pool inventory and schedules long-running work through durable workflows. It reuses the existing ephemeral provider wherever practical rather than reimplementing Terraform and GitOps orchestration.

02 · Starting point

Build on the lifecycle that already works.

The current developer workflow has most of the expensive lifecycle logic, but it is driven from a workstation and tracks environments in a local file. The manager adds shared inventory, asynchronous orchestration, and controlled access.

A

Provision

ci/ephemeral-provider creates an environment-specific Git branch, bootstraps its pipeline, and waits for regional and management provisioning.

B

Redirect & resync

The local CLI can swap an environment to a repository/branch and resync it, so a pre-warmed baseline can be prepared for a checkout.

C

Teardown

The provider purges platform resources, tears down infrastructure and its pipeline, and removes the managed CI branch on successful cleanup.

Today, scripts/dev/ephemeral-env.sh is a local wrapper and .ephemeral-envs is local state. Neither should become the service’s source of truth.

03 · Proposed system

A thin API; durable orchestration underneath.

Keep request handling short and move provisioning, resync, and teardown into tracked background operations. Use the existing provider as the lifecycle engine, packaged in a controlled worker runtime.

04 · Lifecycle

One environment, one owner, one clear path.

Maintain baseline

Reconciler provisions unique environment IDs until the pool has its desired number ready.

Reserve atomically

One available record transitions to checkout-pending in a conditional transaction.

Apply requested ref

Provider swaps/resyncs to the approved repository and branch; service records the resolved commit SHA.

Use & operate

Checkout owner can request a branch change or resync and can inspect operation status.

Release & replace

Release triggers teardown. Only after confirmed cleanup does reconciliation create a fresh baseline.

StateMeaningAvailable for checkout?
provisioningBaseline is being created.No
availableProvisioned baseline, unassigned, and healthy.Yes
checkout-pendingReserved; requested branch is being applied.No
checked-outAssigned to one authenticated owner; updates may be running.No
releasingBeing purged and destroyed after release or expiry.No
quarantinedProvisioning, update, or cleanup failed or has uncertain outcome.No

A failed teardown must never put an environment back into the ready pool. Quarantined resources require an observable retry or operator-reviewed cleanup path.

05 · API contract

Small surface area, asynchronous by default.

Use a checkout as the caller’s ownership handle. Return 202 Accepted plus an operation resource for actions that launch provider work.

POST/v1/checkouts

Reserve a ready environment; optionally request repository and branch.

Caller
GET/v1/checkouts/{id}

Read assignment, environment details, current ref, and status.

Owner / admin
POST/v1/checkouts/{id}/branch

Swap to an approved repository and branch.

Owner / admin
POST/v1/checkouts/{id}/resync

Apply the latest source ref and configured environment changes.

Owner / admin
POST/v1/checkouts/{id}/release

Release ownership and begin destruction; do not reuse the environment.

Owner / admin
GET/v1/operations/{id}

Poll provisioning, branch update, resync, or teardown result.

Authorized caller

Admin-only endpoints can report pool capacity and trigger carefully scoped maintenance actions. Use idempotency keys for checkout and release requests to make retries safe.

06 · Capacity policy

Schedule the ready floor; cap the total fleet.

Pool settings

  • Day and overnight minimum ready counts, with timezone and weekday policy.
  • Maximum total environments and maximum simultaneous provisioning jobs.
  • Baseline repository/ref, config version, region, and allowed target accounts.
  • Approved repositories, maximum checkout duration, and idle lease policy.

Reconciliation rules

  • Count only healthy, unassigned available environments toward the ready floor.
  • Provision asynchronously to fill a deficit, respecting concurrency and total caps.
  • When the floor drops, remove idle available capacity first; never interrupt active checkouts.
  • Failed or stale jobs are surfaced and quarantined instead of silently counted as ready.

Capacity is not instantaneous. Scheduling raises the target ready count, while provisioning still takes time. Record time-to-ready and checkout wait time so the pilot can tune the pool size against actual demand and cost.

07 · Ownership & security

Make the inventory the authority to act.

“Only the environments it controls” must be enforced by design, not by trusting a caller-provided ID or relying on resource naming alone.

Non-negotiable boundaries

  • Generate environment IDs server-side. Every operation resolves to a manager-owned registry record.
  • Fix the target account and region allowlist in service configuration; never accept account IDs from callers.
  • Before destructive work, verify pool ownership, reserved prefix, and recorded Terraform state locations.
  • Bind each checkout to an authenticated principal. Restrict updates and release to that owner or an administrator.
  • Validate and allowlist GitHub repositories/refs; record source commit SHA and audit actor/action.
  • Use a managed GitHub App credential or similarly scoped bot credential in the worker, not a caller token.

Recommended account boundary

Deploy the API and orchestration in the central account. Give the worker dedicated roles that can reach only explicitly configured regional and management accounts. Apply resource-prefix, tag, and state-key restrictions wherever AWS supports them.

If the existing Terraform and bootstrap roles cannot be narrowed safely in shared accounts, use target accounts dedicated to the managed pool. Review account-wide primitives and quotas before expanding concurrency.

Important existing constraint · broad role assumption

The current provider uses OrganizationAccountAccessRole in its cross-account path. That is broader than a strict manager-only boundary. The implementation must replace or constrain this trust path before claiming that the service can affect only its own environments.

08 · Delivery path

Prove the warm-pool workflow before scaling it.

Phase 1 · Validate

Run a two-environment lifecycle spike

Provision baseline environments, then test checkout, branch swap, resync, release, teardown failure, and replacement. Measure provisioning duration, steady-state cost, and shared-account limits.

Phase 2 · Specify

Lock down contracts and safety

Define API schema, pool config, states, ownership, auth, GitHub restrictions, leases, idempotency, role boundaries, and failure recovery.

Phase 3 · Build

Create the standalone control plane

New repository for API, infrastructure-as-code, workflow definitions, registry model, worker image, deployment instructions, and operational dashboards.

Phase 4 · Integrate

Package and pin the provider

Expose structured service inputs/results; keep the provider as the lifecycle engine. Make worker versions traceable and repeatable instead of shelling out to local Make targets.

Phase 5 · Pilot

Start with one capped pool

Enable a small daytime/overnight schedule, test IAM and cleanup failure paths, tune from latency and cost metrics, then expand gradually.

Reliability signals

Provision/resync/teardown success rate, quarantined count, stale operations, job retries.

Experience signals

Ready pool depth, checkout wait and time-to-ready percentiles, lease age, branch-update latency.

Cost signals

Environment hours by pool and owner, idle-ready hours, replacement rate, account spend.

09 · Decisions to settle

Questions for the design review.

Where do pooled environments live?

Shared development target accounts with restricted roles, or dedicated regional/management accounts for the pool?

Who can check out?

Which internal identities and CI workloads are allowed, and what identity provider/authorizer should the API use?

What can be built?

Which repositories, organizations, and branch/ref patterns are trusted to run through the environment pipelines?

What is the capacity envelope?

Day/night ready counts, timezone, weekends, maximum total fleet, concurrent builds, and cost ceiling?

How is the provider versioned?

Worker image built from a release in rosa-seaplane, a versioned package, or another immutable artifact?

What is the cleanup policy?

Maximum checkout age, abandoned lease behavior, retry window, and who can inspect or force-clean quarantined environments?

Outcome: a reusable, centrally operated pool can reduce the wait before tests start while preserving a clean environment per checkout. The core trade-off is deliberate: keep baseline infrastructure running to improve checkout latency, but destroy every returned environment and restore capacity asynchronously.
